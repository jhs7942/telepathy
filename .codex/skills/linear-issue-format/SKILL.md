# Linear 이슈 형식

텔레파시 개발 작업을 시작하기 전에 Linear 이슈를 만든다. 이슈는 개발자가 아니어도 목적과 범위를 이해할 수 있게 작성하고, 상세 구현 로그는 Pull Request 또는 Linear 개발 메모에 둔다.

## 작업 시작 규칙

1. 코드나 설정을 바꾸기 전에 Linear 이슈를 만든다.
2. 생성된 이슈 식별자를 확인한다. 예: `TEL-39`.
3. 이슈 식별자와 같은 이름의 Git 브랜치를 만든다.
4. 브랜치에서 작업을 시작할 때 이슈 상태를 `In Progress`로 바꾼다.

이슈 생성이 실패했거나 식별자를 확인하지 못했으면 브랜치를 만들거나 코드를 수정하지 않는다. CLI 재시도 전에는 실패 원인을 확인해 중복 이슈를 만들지 않는다.

## 이슈 기본 속성

사용자가 다른 값을 지정하지 않으면 다음을 기본으로 한다.

- 담당자: 본인
- 우선순위: 중간
- 프로젝트: 관련된 텔레파시 MVP 프로젝트
- 라벨: 작업 성격에 맞는 팀 라벨

설정·문서·개발 환경 작업에는 `type/chore`, 설계 단계 작업에는 `phase/design`을 사용한다. 기능·버그 작업에는 실제 성격에 맞는 라벨을 먼저 확인한다.

## 설명 형식

이슈 설명은 Markdown 제목과 문단, 목록으로 작성한다. 한 문단에 여러 목적을 나열하지 않고, 아래 항목을 같은 순서로 사용한다.

```markdown
## 작업 내용

작업의 목적과 사용자 또는 서비스에 미치는 결과를 짧은 문단으로 작성한다.

## 변경 범위

- 포함하는 변경을 목록으로 작성한다.
- 포함하지 않는 중요한 범위가 있으면 함께 작성한다.

## 완료 기준

- 완료 여부를 판단할 수 있는 결과를 목록으로 작성한다.

## 예상 소요 시간

**약 N시간 또는 N일**

예상에 포함한 작업과 일정이 달라질 수 있는 조건을 한 문장으로 작성한다.
```

예상 소요 시간은 약속이 아니라 현재 범위와 확인된 의존성을 기준으로 한 추정이다. 외부 승인, 배포 환경, 미확인 호환성처럼 일정에 영향을 주는 조건은 함께 적는다.

## 갱신과 완료

- 범위나 예상 시간이 달라지면 같은 형식으로 이슈 설명을 갱신한다.
- Pull Request와 Linear 개발 메모는 `docs/conventions/git-workflow.md`의 다섯 항목 형식을 사용한다.
- 검증과 Pull Request 스쿼시 머지가 끝난 뒤 이슈를 `Done`으로 바꾼다.
