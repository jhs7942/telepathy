# Linear와 GitHub 작업 흐름

## 목적

해야 할 일, 코드 변경, 배포 이력을 같은 작업 단위로 연결한다. Linear 이슈는 무엇을 왜 하는지 기록하고, Git 브랜치는 그 작업의 코드 변경을 담는다.

## 작업 시작

1. Linear에 작업 이슈를 만든다.
2. 이슈 식별자를 브랜치명으로 사용한다. 예: `TEL-12`
3. 이슈 상태를 `In Progress`로 바꾼 뒤 해당 브랜치에서 작업한다.

하나의 브랜치에는 하나의 Linear 이슈만 담는다. 범위가 달라지면 새 이슈와 새 브랜치를 만든다.

## 작업 완료

1. 변경 범위에 맞는 검증을 실행하고 결과를 이슈에 기록한다.
2. 브랜치를 원격 저장소에 push한다.
3. GitHub에서 Pull Request를 만들고 Linear 이슈를 연결한다.
4. 검토가 끝나면 Pull Request를 **스쿼시 머지**한다.
5. 병합이 끝난 뒤 Linear 이슈를 `Done`으로 바꾼다.

스쿼시 머지는 하나의 작업 이슈가 기본 브랜치의 하나의 명확한 커밋으로 남게 한다. 원래 브랜치는 병합 후 삭제한다.

## 기록 원칙

- Linear 이슈 제목과 설명은 개발자가 아니어도 목적과 결과를 이해할 수 있게 작성한다.
- 구현 세부 사항, 명령어, 상세 검증 로그는 이슈의 개발 메모 또는 Pull Request 설명에 둔다.
- 커밋 메시지는 기존 규칙대로 `<type>: <한국어 요약>` 형식을 사용한다.
- 브랜치 생성, push, Pull Request 생성, 병합은 사용자가 요청하거나 승인한 작업 범위 안에서 수행한다.

## Pull Request 기록 형식

모든 Pull Request 설명은 아래 다섯 항목을 같은 순서로 작성한다. Linear 이슈의 개발 메모에도 필요한 항목을 같은 형식으로 남긴다.

```markdown
## 작업 내용

- 해결하려는 문제와 완료한 목표를 작성한다.
- Linear 이슈: `TEL-번호`

## 변경사항

- 사용자에게 보이는 변화와 주요 코드·설정 변경을 작성한다.

## 테스트 증적

- `실행한 명령어` — 통과 또는 실패 결과
- 검증하지 못한 항목은 이유를 작성한다.

## 확인해야 할 것

- 검토자 또는 배포 전에 확인할 사항을 작성한다.
- 없으면 `없음`으로 작성한다.

## 다음 작업

- 이번 Pull Request에 포함하지 않은 후속 작업을 작성한다.
- 없으면 `없음`으로 작성한다.
```

테스트 증적에는 실제로 실행한 명령어와 결과만 기록한다. 실행하지 않은 테스트나 추정 결과를 통과한 것처럼 적지 않는다.
